# Phase 1 — Launch: a complete daily practice

## Goal

A devotee can install the app on iOS or Android, or open it on the web, pick a practice — a mantra or a deity's 108 names — chant every day in several ways, and see their progress, all offline. Scope from the [roadmap](../../product/roadmap.md#phase-1--launch-a-complete-daily-practice).

Milestones are in build order. Each should end in a working app.

## Scope

- **In:** everything in the P1 row of the roadmap — mantras and namavalis, the P1 chanting modes, the session screen, the content pipeline, onboarding, sankalpas and progress, Navaratri, starter articles, optional accounts and sync.
- **Out:** stotras, custom namavalis, voice counting, smartwatch, chant along, listening japa, the Sikh, Buddhist and Jain libraries, community and temples. These are P2 and later.

- [x] npm workspaces monorepo: `apps/mobile` (Expo SDK 57, Expo Router), `packages/shared`
- [x] Shared domain logic: round progress, word-sequence tap, likhita matching, grace-day streaks — with tests
- [x] First chanting screen: mala tap and word-by-word, haptics, keep-awake, offering prompt at each mala
- [x] Lint, type-check, tests, static web export; CI workflow
- [x] CLAUDE.md, TECH-VERSIONS.md, setup guide

The [practice model](../../decisions/2026-09-22-practice-model-ordered-steps.md), [content packs](../../decisions/2026-09-22-content-packs.md), [grouped count events](../../decisions/2026-09-22-grouped-count-events.md) and [guest-first accounts](../../decisions/2026-09-22-guest-first-accounts.md) all landed after it. Nothing has shipped, so there is no data to migrate ([what changes](../../architecture/data-model.md#changes-to-existing-code)).

## Early spikes

**S4 must finish before any local storage is built** (M3): PowerSync brings its own SQLite layer, so building on `expo-sqlite` first would mean migrating twice ([why](../../architecture/data-model.md#sync-engine)). S1, S2 and S3 run alongside M1 and M2.

- [ ] **S1 — Indic scripts on devices:** Devanagari, Gurmukhi, Tamil rendering on real iOS and Android phones (web ✅ Devanagari). Choose Noto font set.
- [ ] **S2 — Voice counting prototype:** record a mantra 3×, count repeats on-device. Compare LiteRT keyword spotting vs Picovoice (accuracy, licence cost). Informs P2.
- [ ] **S3 — iOS volume buttons:** feasibility and App Store acceptability of volume-change observation.
- [ ] **S4 — Sync approach:** PowerSync vs our own Supabase sync, against the seven criteria in [data-model](../../architecture/data-model.md#sync-engine). **PowerSync accepted** ([decision](../../decisions/2026-09-22-sync-engine-powersync.md)); criteria 4–7 are closed on the vendor's docs, though 7 also depends on our own position merge function, which only the prototype exercises. The prototype is what remains, and all it needs is a Supabase project, a free-plan PowerSync instance and a custom dev client:
  - [x] Owner accepts the decision, since it commits us to a paid service
  - [ ] Guest chants offline in `localOnly` tables, signs in, counts arrive in the account — on React Native, where the documented recipe is unproven
  - [ ] Two devices chant the same practice offline on the same version and pass, reconnect: `totalCount` exact, one position with marks unioned
  - [ ] Same, but one device finishes the pass first: the later pass wins and the other device's marks are not unioned in
  - [ ] Expo Router web export serves the worker assets and persists offline, Safari included

## M1 — Domain rework in `packages/shared` ✅

Pure logic and types, all tested. No storage, so this does not wait on S4. Shapes follow the [data model](../../architecture/data-model.md); fields stay snake_case.

- [x] `Practice` with `kind` (`mantra` · `namavali`), `version`, `steps`, `default_round`, `repetition_word`; `Step` with `text`, `words`, `name`, `meaning` ([practice](../../architecture/data-model.md#practice), [step](../../architecture/data-model.md#step))
- [x] `Tradition`, `Deity` (with `parent_id`) and `Program` ([catalog](../../architecture/data-model.md#catalog))
- [x] `mantra_id` becomes `practice_id` everywhere; a practice id is a catalog slug or a custom practice's UUID
- [x] `Script` gains `iast`; `latin` means the simple common spelling
- [x] `ChantMode` gains `manual` and `correction`
- [x] `CountEvent` gains `local_day`, `tz_offset_min` and `steps_per_repetition`; totals group by `local_day`, never by converting `created_at`
- [x] `Session` carries `practice_version` and `steps_per_repetition`
- [x] `PracticePosition` and its merge rule: `practice_version`, then `pass_ordinal`; within the same version and pass, **union** `chanted_steps` and take only `step_index` from the higher `hlc`, so a name chanted on either device stays chanted ([merging positions](../../architecture/data-model.md#practiceposition))
- [x] `Sankalpa` gains `program_id`, `intention`, `status` and sync fields
- [x] UUIDv7 generation; hybrid logical clock — issue, compare, and move forward on receive ([conflict rule](../../architecture/data-model.md#conflict-rule))
- [x] Counting: repetitions, recitations and **names chanted** (`count × steps_per_repetition` as stored on the event); per-session totals floored at zero; streaks unchanged ([counting](../../architecture/data-model.md#counting))

## M2 — Content pipeline ([spec](../../architecture/content-pipeline.md))

The catalog has to exist before any screen can read a practice.

- [x] Content and export schemas in `packages/shared` ([Zod](../../decisions/2026-09-23-schema-library-zod.md)), used by both the content build and the app; catalog ids must match `^[a-z0-9-]+$`, which the [derived ids](../../architecture/data-model.md#ids-for-rows-that-are-unique-per-devotee) rely on — the one M1 item left, moved here because the content build is its first consumer
- [x] `content/` source tree: traditions, deities, practices and programs, as YAML — the five development mantras and their deities, unreviewed; programs come with M8 and M9
- [x] Schema validation against `packages/shared`, plus layout and cross-file references, in `tools/content-build`; runs in `npm test`, so in `npm run check` and CI
- [x] Choose the transliteration library: vidyut-lipi ([decision](../../decisions/2026-09-23-transliteration-library.md))
- [x] Generate `latin` and the other Indic scripts from the source script and IAST ([transliteration](../../architecture/content-pipeline.md#transliteration)); check the source against the hand-written IAST, and round-trip the scripts that can. Writing the generated text to packs, and the reviewed snapshot, come with the build script
- [ ] Per-script conventions (nasals, ॐ, Tamil marks) as tested rules after transliterating, each signed off by a reader of that script before it ships
- [x] Report vidyut-lipi's IAST bug upstream (`sāī` read as सी): [ambuda-org/vidyut#253](https://github.com/ambuda-org/vidyut/issues/253)
- [ ] Build script: validate, generate, build packs, write the manifest, sign it (Ed25519), publish ([plan](2026-09-24-content-build-and-packs.md), all but publishing)
- [ ] Pack layout: `index`, `core`, `deity/<id>`, script and language add-ons, `programs` ([packs](../../architecture/content-pipeline.md#packs))
- [ ] Content signing key held by the owner, never in CI; the app ships the current and next public keys
- [ ] Choose pack and audio hosting (Supabase Storage or Cloudflare R2) and close the [open question](../../product/open-questions.md#content-hosting)
- [ ] Production packs refuse unreviewed content; development packs include it, flagged

## M3 — Foundations (after S4)

- [ ] Local storage for count events, sessions, practices, positions and settings, using the layer S4 chose
- [ ] Repositories in `apps/mobile/src/data/` as the only code that touches storage ([layers](../../architecture/data-model.md#layers))
- [ ] Derive the ids of rows that are unique per devotee — profile, saved practices, deity defaults, positions — as UUIDv5 from the documented namespace and name, with fixed test vectors, instead of generating them, so two offline devices write one row and the merge can run; recompute them on every re-key: sign-in, keeping practice as a guest after deleting the account, and import ([ids](../../architecture/data-model.md#ids-for-rows-that-are-unique-per-devotee)). `OwnedRecord` in `packages/shared` still documents every `id` as a generated UUIDv7 and the pre-sign-in `user_id` as the local profile id; update both (local owner id)
- [ ] Catalog tables and full-text search index; packs install and update into them, never wiped ([device](../../architecture/content-pipeline.md#device))
- [ ] Core bundle shipped inside the app; a signed `core` pack with a higher version replaces it
- [ ] Device ID and session model; replace the in-memory session hook
- [ ] i18n setup; UI languages TBD ([open question](../../product/open-questions.md#languages-at-launch)) — build with English and one Indic language to prove the pipeline
- [ ] Theme tokens for light and dark; the session screen stays dark
- [ ] Navigation shell: Chant (home) · Progress · Programs · Learn · Settings

## M4 — Chanting modes ([spec](../../product/features/chanting-modes.md))

Every mode feeds one count. Which modes each practice type supports: [modes by practice type](../../product/features/chanting-modes.md#modes-by-practice-type).

- [ ] Mala tap: bead-ring visual, round size setting (108 / 54 / 27 / 33 / custom), meru haptic, optional bell
- [ ] Namavali name by name: the current name large, bead _n_ is name _n_, back one name, position saved and restored ([spec](../../product/features/chanting-modes.md#namavali-name-by-name))
- [ ] Mala styles (Rudraksha, Tulsi, crystal, sandalwood, lotus seed, simarna, plain), all open from day one
- [ ] Word-by-word tap with memory mode (hide words) — mantras only
- [ ] Likhita japa typing and digital japa book pages
- [ ] Silent chanting: pace mode and breath mode (marked estimated)
- [ ] Volume-button counting (Android first; iOS per S3)
- [ ] Flip face down to pause
- [ ] Manual log and corrections as their own event kinds
- [ ] Mode switching mid-session, all feeding one count
- [ ] Finishing a pass is one local transaction: the recitation's count event is written and `chanted_steps` reset together, so a crash can't do one without the other ([finishing a pass](../../architecture/data-model.md#practiceposition))
- [ ] A recitation counts where it was chanted — events are unique by id and nothing else is deduplicated, so the same pass completed offline on two devices counts twice

- [ ] Supabase project, schema in `supabase/`, row-level security on every user table
- [ ] Optional sign-in: email code, Google, Apple
- [ ] Consent before any account data is downloaded or uploaded

- [ ] Web: COOP/COEP headers, redirect OAuth, a PWA service worker, `navigator.storage.persist()`

## Risks and open questions

- **S4 gates M3.** PowerSync is chosen, but until the prototype passes, no local storage can be built without risking a rewrite.
- **expo-sqlite's web support is alpha** ([web](../../architecture/data-model.md#web)). Fallback: an IndexedDB store behind the same repositories.
- **Advisor availability** gates production content, and so the launch library.
- **The account age policy needs a lawyer** before launch ([open question](../../product/open-questions.md#account-age-policy)).
